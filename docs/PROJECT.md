# Project

## Overview
Motor-drive firmware for a custom STM32G473 board driving a BLDC/PMSM motor through a DRV8350S gate driver. Field-oriented control with the rotor angle from Hall sensors or from a sensorless sliding-mode back-EMF observer; ThreadX RTOS; CANopen node (CANopenNode on FDCAN1) with CiA 402 drive profile (state machine, profile velocity and profile torque modes; PDO mapping and robustness still to do); Scrutiny embedded debugger for live variables and datalogging.

## Architecture
Three layers (see `doc/motor_control/README.md`, local only):
- `App/` — owns the hardware and timing: ISR (`isr.cpp`), ADC measurements (current offset measured in the ADC3 ISR), `Supervisor` state machine (INIT state does the one-time peripheral start-up), `StartupSeq` (Hall calibration, open-loop I/f start), `Monitor` (faults), CANopen application and the bridge to the motor (`canopen_app.c`, `canopen_bridge.cpp`: 0x2000–0x2012 objects, CiA 402 state machine on 0x6040/0x6041, modes of operation 0x6060/0x6061 (profile velocity / profile torque with `motor_control::Ramp`), fault → 0x603F + EMCY), Scrutiny glue.
- `motor_control/` — hardware-independent C++20 FOC library (transforms, current/speed PI, SVPWM, Hall sensor, SMO observer, PLL, startup, state machine). Never touches registers, HAL or interrupts; works on physical units; the same sources build for the target and for host unit tests (`tests/`).
- `canopen/` — CANopenNode stack, STM32 FDCAN driver (`CANopenNode_STM32/`) and the project's own object dictionary (`od/`: `OD.c/h`, `bldc_drive.eds/.xdd`).
- Third party: `scrutiny-embedded/`, CubeMX-generated `Core/`, `Drivers/`, `Middlewares/`, `AZURE_RTOS/`, `USBX/`.
Rules:
- `motor_control/` stays hardware-free: no HAL, registers, ThreadX or interrupt code; only math on physical units, so it keeps building and testing on the PC.
- Control-loop ISRs stay short: no blocking, no waiting, no dynamic memory and no blocking ThreadX calls inside an ISR.
- No dynamic memory in the firmware (no `malloc`/`new`, no heap-backed containers such as `std::vector`); use static allocation.
- Do not modify third-party code (`canopen/CANopenNode/`, `canopen/CANopenNode_STM32/`, `scrutiny-embedded/`, ThreadX/USBX under `Middlewares/`); adapt in our own layer. An exception needs the user's approval.

## Environment

- Toolchain: GNU Arm `gnu-tools-for-stm32` 14.3.1 from the STM32Cube bundles (`%LOCALAPPDATA%/stm32cube/bundles/gnu-tools-for-stm32/14.3.1+st.2/bin`), not on the system PATH. CMake + Ninja, presets `Debug` / `Release` (`CMakePresets.json`, toolchain file `cmake/gcc-arm-none-eabi.cmake`).
- Scrutiny CLI (`C:/Program Files (x86)/Scrutiny Debugger`): if found, a post-build step writes `<name>_tagged.elf` and `.sfd`; the board should run the tagged ELF. Without the CLI the build still works.

These are the same tools the VS Code extension uses (`cube-cmake`), so the existing `build/` cache stays valid. Verified 2026-10-25: `cmake --build --preset Debug` builds from bash.
- Host tests: GoogleTest sources in `tests/` (gtest fetched by CMake), but there is no host-side CMake project or preset that builds them yet; a host compiler (WinLibs MinGW g++) is installed. See WORK.md › Open questions.
- Git hosting: private GitHub repo `MCanKandamar/stm32g4-foc-motor-drive` (remote `origin`, MIT licence). Changes reached `main` through pull requests (merge commits) until 2026-10-27; since then the user works directly on `main` (see Decisions). `gh` CLI is not installed locally. `CLAUDE.md` (tracked) only imports `AGENTS.md` (`@AGENTS.md`), so Claude Code sessions, including cloud sessions, load the project rules; personal notes go to the untracked `CLAUDE.local.md`.
- CI/CD (GitHub Actions, `.github/workflows/`): `build.yml` builds Debug and Release on every push (ubuntu-latest, Arm GNU 14.3.Rel1 via `carlosperate/arm-none-eabi-gcc-action@v1`, Ninja from apt), prints size and uploads `.elf`/`.map` artifacts (14 days); `release.yml` runs on `v*` tags and publishes a GitHub Release with Release `.elf`/`.hex`/`.bin`. Scrutiny is absent in CI, so CI ELFs are not tagged for Scrutiny.
- CAN bench: the user's own STM32F072 SLCAN adapter and the CANdamar PC tool (formerly CANviz) (raw frames, SDO, CiA 402 commands); bus 500 kbit/s; drive node-ID 13.
- Agent HW tests (2026-10-30): scripts in `tools/hil/` — `test_cia402_v2.py` (CiA 402 state machine), `test_pdo.py` (PDO + SYNC), `hall_speed_capture.py` (Scrutiny datalog, Hall vs SMO speed), `speed_step.py` (speed-loop step / ramp response with metrics; can write the speed PI gains to RAM), `drive_util.py` (status, fault reset, Hall calibration), `scrutiny_link.py` (Scrutiny connection); motor tests need `--motor-ok`; logs in the ignored `tools/hil/logs/`. SLCAN adapter on COM15 (python-can 4.6, `interface='slcan'`); board USB CDC for Scrutiny on COM6 (VID 0x0483, PID 0x5710). Datalogging: 20 kHz FOC loop, 8 KB buffer. After the SLCAN channel was closed the node may be pre-op (no ACK → TX overflow): wait for 0x1001 bit 4 = 0, then send NMT start.

## Hardware & toolchain
- Target: STM32G473VET6 (LQFP100, Cortex-M4F, `-mfpu=fpv4-sp-d16 -mfloat-abi=hard`) on a custom board; gate driver DRV8350S (SPI2), current-sense amplifiers AD8418.
- Toolchain & build: arm-none-eabi-gcc 14.3.1, CMake ≥ 3.22 + Ninja; C11, C++20. Build and size commands: see AGENTS.md › Commands.
- Code generator: STM32CubeMX (`015_BLDC_FOC_RTOS_MotorDrive.ioc`, toolchain CMake, `KeepUserCode=true`). Generated: `Core/`, `Drivers/`, `Middlewares/`, `AZURE_RTOS/`, `USBX/`, `cmake/stm32cubemx/`, `startup_stm32g473xx.s`, `STM32G473xx_FLASH.ld`. Edit generated files only inside `USER CODE` blocks. The root `CMakeLists.txt` is generated once and is free to edit.
- Pins, clocks, peripherals: HSE 24 MHz → PLL → SYSCLK 170 MHz. TIM8 centre-aligned PWM, period 4250 (≈ 20 kHz): high side INH_A/B/C = PC6/PC7/PC8, low side INL_A/B/C = PC10/PC11/PC12. Hall HAL_A/B/C = PA6/PA7/PB0 (TIM3). Phase currents CURR_A/B/C = PD13/PD11/PE8; phase voltages SENS_A/B/C = PD14/PD12/PD10; DC bus SENS_VDC = PA8 (ADC3/4/5). DRV8350S: SPI2, DRV_CS = PB12, DRV_ENABLE = PD15, FAULT_N = PE0. FDCAN1 RX/TX = PD0/PD1. LEDs: CAN_LED = PD2, PROCCESS_LED = PE1. Also CORDIC, DMA, USB.
  The pin, clock and peripheral setup in the `.ioc` is fixed; no other reserved pins or limits recorded (changes need the user's approval, see AGENTS.md › Always ask first).
- RTOS & memory budget: Azure RTOS ThreadX; threads Init (2 KB stack), Supervisor (2 KB), Monitor (1 KB), CANopen (2 KB) in `Core/Src/app_threadx.c`. Flash 512 KB, RAM 128 KB (linker script). Last measured 2026-10-23: Debug flash 175.4/512 KB, RAM 66.3/128 KB; Release flash 101.9/512 KB, RAM 66.2/128 KB.
  No explicit memory budget: report flash/RAM use with every build and flag large jumps. Thread stacks are statically allocated arrays in `app_threadx.c`.
- Debug & flashing setup: ST-Link via VS Code (`.vscode/launch.json`, `stlinkgdbtarget`), loads `build/Release/015_bldc_foc_rtos_motordrive_tagged.elf`. For information only; flashing needs the user's approval every time.

- 2026-10-30 · Decision: in Hall mode the speed PI uses the speed of the Hall angle PLL (`meas.speed_rpm_hall_pll`, PLL bandwidth 30 Hz), not the 24-edge average (`meas.speed_rpm_hall`, still used for 0x606C/0x2001 and Scrutiny); speed PI Kp = 0.0025 A/rpm, Ki = 0.02 A/(rpm·s), tuned on the board (was 0.003 / 0.003, then the user's 0.001 / 0.001, which was stable but slow: ~250 rpm behind a 1000 rpm/s ramp). Measured plant: friction ≈ 0.18 A, K ≈ 20 000 rpm/(s·A); the 30 Hz speed PLLs (Hall and SMO) limit the speed loop to ~8 Hz crossover; a step on 0x2010 overshoots 17–30 %, ramps (0x6083) much less · Why: the 1-turn average lags T/2 (30 ms at 1000 rpm, 60 ms at 500), which costs ~65° phase at the 6 Hz loop crossover at 1000 rpm and made the loop oscillate below ~1000 rpm (Scrutiny datalog 2026-10-30).
- 2026-10-30 · Decision: all code comments in short, simple English, and only where needed (rule in AGENTS.md › Conventions); the Turkish comments in our own files were translated with no code change; the Turkish text inside code (the CMake `message()` for a missing Scrutiny CLI, the prompts in `tools/hil/test_cia402_v2.py`) was translated too · Why: user's choice, so anyone can read the code.
- 2026-10-27 · Decision: work directly on `main` for now. A cloud agent commits unsigned with author/committer "Muslum Can Kandamar <cankandamarr@gmail.com>" and no AI trailers, pushes, and gives the user PowerShell commands to re-sign the new commits (`git rebase --exec "git commit --amend --no-edit -S"`) and push with `--force-with-lease` · Why: user's choice (single developer); a cloud session cannot sign with the user's SSH key.
- 2026-10-27 · Decision: PDO set (node 13, COB-ID = base + node-ID, added by the stack) — RPDO1 0x20D = 0x6040 + 0x60FF (pv), RPDO2 0x30D = 0x6040 + 0x6071 (tq), both type 0xFE (applied on receipt); TPDO1 0x18D = 0x6041 + 0x606C, TPDO2 0x28D = 0x6041 + 0x6077 + 0x6061, type 0xFE, event timer 100 ms, inhibit 0; PDO 3–4 stay disabled. The drive is a SYNC consumer only (0x1005 = 0x80, 0x1006 = 0); synchronous TPDOs by setting 0x18xx:02 = 1..240. No RPDO timeout yet (phase 7). DBC for CANdamar: `canopen/od/bldc_drive.dbc` · Why: one PDO pair per mode keeps each frame ≤ 6 bytes and matches CiA 402 practice; 100 ms is enough for CANdamar monitoring at low bus load.
- 2026-10-27 · Decision: phase 5 details — 0x2012 sensor mode (0 = sensorless, 1 = Hall) applies to profile velocity only; profile torque always starts with Hall. 0x2010 stays as a speed reference without ramp: a new 0x2010 value sets the ramp output and copies itself to 0x60FF (last write of 0x2010/0x60FF wins). 0x6060 and 0x2012 accept only 3/4 and 0/1; a different value in Operation Enabled → SDO abort 0x08000022 (same value is accepted, so a cyclic RPDO does not fail). Ramps run in the CANopen thread (1 ms) and start when the motor reaches CLOSED_LOOP (pv starts from the actual speed, tq from 0). Defaults 0x6083 = 0x6084 = 1000 rpm/s, 0x6087 = 1000 ‰/s. Statusword: pv bit 10 = ramp at target and |actual − target| ≤ 30 rpm, bit 12 = |actual| ≤ 10 rpm; tq bit 10 = ramp at target. Torque target clamped to IQ_REF_MAX (≈ ‰825) · Why: user's choice for sensor mode and 0x2010; the rest keeps the bridge simple.
- 2026-10-27 · Decision: CiA 402 modes of operation — Profile Velocity (3) and Profile Torque (4) only; velocity objects in rpm; pv runs `LoopMode::SPEED` behind a ramp (0x6083/0x6084); tq runs `LoopMode::CURRENT` with iq_ref = T / kt, kt = 0.066 N·m/A (datasheet value in `motor_parameters.hpp`), 0x6076 rated torque = 400 mN·m (continuous torque), id_ref = 0, |iq_ref| ≤ `IQ_REF_MAX` = 5 A (≈ 0.33 N·m, ‰825; provisional, the user will revisit); a write to 0x6060 is accepted only outside Operation Enabled, otherwise SDO abort · Why: user's choice; torque control is current control, rpm matches the existing 0x2010 and CANdamar, mode changes while the motor is driven are avoided.
- 2026-10-27 · Decision: `NMT_CONTROL` overridden in canopen/CMakeLists.txt = STARTUP_TO_OPERATIONAL | ERR_ON_ERR_REG | ERR_REG_COMMUNICATION: only communication errors move the node to pre-operational; motor faults (0x1001 generic bit) do not, they are reported by CiA 402 Fault, so TPDOs keep running. No automatic return to operational (ERR_FREE_TO_OPERATIONAL would override a master's Enter Pre-Operational); the master restarts the node · Why: HW test 2026-10-27 showed NMT 05 → 7F on a motor fault after c68262f.
- 2026-10-27 · Decision: `MotorState` = INIT, IDLE, ALIGN, OPEN_LOOP, CLOSED_LOOP, FAULT, CALIBRATING (0x2002 numbers changed; ADC_OFFSET_CAL removed). INIT runs once at power-up: peripheral start (once per boot) + current offset, then IDLE; STOP is ignored in INIT; RESET_FAULT goes back to INIT if INIT never finished, else IDLE. START is START_HALL (→ CLOSED_LOOP) or START_SENSORLESS (→ ALIGN), chosen by the Supervisor from `cmd.sensor` · Why: init work in one visible place (later DRV8350S SPI, stored calibration); START no longer waits for an offset state.
- 2026-10-27 · Decision: current offset = mean of 128 injected ADC3 samples taken in the FOC ISR with the power stage off (6.4 ms, non-blocking); measured in INIT and refreshed on CiA 402 Switch On (0x07); not single-use — START/CALIBRATE use the latest offset and are deferred only while a refresh runs · Why: the old blocking `adcOffsetCalibration()` busy-polled regular conversions for ~1.1 s in the Supervisor thread (prio 3), starving CANopen and USB (HW test 2026-10-26, T13).
- 2026-10-27 · Decision: CiA 402 Not Ready to Switch On ↔ `MotorState::INIT` (statusword 0x0000, controlword ignored), then Switch On Disabled · Why: matches the standard's power-up state.
- 2026-10-26 · Decision: motor faults reach CANopen as 0x603F (CiA 402 error code: driver nFAULT 0x5000, motor over-current 0x2310, driver over-current 0x2300, over-voltage 0x3210, under-voltage 0x3220, motor over-temp 0x4310, driver over-temp 0x4210, sensor 0x7300, sensorless lost 0xFF01) and one EMCY per change, using CANopenNode error bit 0x40 + `FaultCode` (manufacturer critical range); `CO_CONFIG_ERR_CONDITION_GENERIC` is overridden in `canopen/CMakeLists.txt` so 0x1001 bit 0 is set too · Why: CiA 301 requires the generic bit for any active error; the stack's default only looks at its own bits.
- 2026-10-26 · Decision: CiA 402 state lives in its own variable in `canopen_bridge.cpp`; `MotorState` and `motor_control/` stay unchanged. `MotorState` wins: FAULT → Fault; an Operation Enabled / Quick Stop Active drive that drops to IDLE (stop from Scrutiny or 0x2011, quick stop done) → Switch On Disabled · Why: our `MotorState` has no Ready/Switched On split; falling back to Switch On Disabled stops a controlword left at 0x0F from restarting the motor on its own.
- 2026-10-26 (partly superseded by 2026-10-27: Not Ready to Switch On now used) · Decision: CiA 402 mapping — Switched On = IDLE with the ADC offset measured (DRV and PWM still off until 0x0F; deviation from the standard's "power stage on"); Operation Enabled reported as soon as START is accepted (also during ALIGN/OL); 0x0F starts only from IDLE; Quick Stop = coast (`cmd.stop`, no braking ramp); Fault Reaction Active skipped (power is cut at once); statusword bit 4 = Vdc within limits, bit 9 = 1, bits 7/10 = 0 for now · Why: `powerOn()` enables DRV and MOE together; master timeouts on a ~1 s startup; regen braking is parked.
- 2026-10-26 (superseded by 2026-10-27) · Decision: ADC current offset is measured on the CiA 402 Switch On transition (0x07) and reused by START; START still measures when no valid offset exists. Startup flow unchanged: Hall ADC → CL, sensorless ADC → ALIGN → OL → CL · Why: offset drifts with temperature so it is measured at every switch-on, like real drives; align stays in sensorless because the SMO sees no back-EMF at standstill (e = kₑ·ω = 0).
- 2026-10-26 · Decision: 0x2011 command keeps only 2 = stop and 4 = calibrate; 1 = start and 3 = reset fault are removed · Why: they would bypass the CiA 402 Shutdown → Switch On → Enable Operation sequence; stopping is always safe.
- 2026-10-26 · Constraint: no communication-loss reaction yet — if the CAN master disappears the motor keeps running until phase 7 (heartbeat consumer / 0x6007) · Learned from: CiA 402 mapping review.
- 2026-10-26 · Decision: CI on GitHub Actions with Linux runners and the same Arm GNU version as the local STM32Cube bundle (14.3) · Why: cheapest runners; matching compiler avoids "builds in CI but not locally" differences.
- 2026-10-23 · Decision: CANopenNode runs in its own ThreadX thread (priority 5) that calls `canopen_app_process()` and `canopen_app_interrupt()` every 1 ms; no TIM7 timer interrupt · Why: user's choice, keeps the stack out of ISRs.

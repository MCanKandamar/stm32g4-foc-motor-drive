## Overview
Motor-drive firmware for a custom STM32G473 board driving a BLDC/PMSM motor through a DRV8350S gate driver. Field-oriented control with the rotor angle from Hall sensors or from a sensorless sliding-mode back-EMF observer; FreeRTOS; CANopen node (CANopenNode on FDCAN1) with CiA 402 drive profile (state machine, profile velocity and profile torque modes, PDO mapping, reaction to communication loss); Scrutiny embedded debugger for live variables and datalogging.

## Architecture
Three layers (see `doc/motor_control/README.md`, local only):
- `App/` — owns the hardware and timing: ISR (`isr.cpp`), ADC measurements (current offset measured in the ADC3 ISR), `Supervisor` state machine (INIT state does the one-time peripheral start-up), `StartupSeq` (Hall calibration, open-loop I/f start), `Monitor` (faults), CANopen application and the bridge to the motor (`canopen_app.c`, `canopen_bridge.cpp`: 0x2000–0x2012 objects, `motor_control::Cia402` wired to 0x6040/0x6041, modes of operation 0x6060/0x6061 (profile velocity / profile torque with `motor_control::Ramp`), fault → 0x603F + EMCY), Scrutiny glue, TinyUSB setup (`usb_descriptors.c`, `tusb_config.h`).
- `motor_control/` — hardware-independent C++20 FOC library (transforms, current/speed PI, SVPWM, Hall sensor, SMO observer, PLL, startup, state machine, CiA 402 state machine `cia402`). Never touches registers, HAL or interrupts; works on physical units; the same sources build for the target and for host unit tests (`tests/`).
- `canopen/` — CANopenNode stack, STM32 FDCAN driver (`CANopenNode_STM32/`) and the project's own object dictionary (`od/`: `OD.c/h`, `bldc_drive.eds/.xdd`).
- Third party: `scrutiny-embedded/`, `tinyusb/` (versions in `tinyusb/VERSIONS.md`), CubeMX-generated `Core/`, `Drivers/`, `Middlewares/` (FreeRTOS).
Rules:
- `motor_control/` stays hardware-free: no HAL, registers, RTOS or interrupt code; only math on physical units, so it keeps building and testing on the PC.
- Control-loop ISRs stay short: no blocking, no waiting, no dynamic memory and no blocking FreeRTOS calls inside an ISR. ADC3 and EXTI0 make no RTOS calls at all (they are above the FreeRTOS mask).
- No dynamic memory in the firmware (no `malloc`/`new`, no heap-backed containers such as `std::vector`); use static allocation.
- Do not modify third-party code (`canopen/CANopenNode/`, `scrutiny-embedded/`, `tinyusb/src/`, FreeRTOS under `Middlewares/`); adapt in our own layer. An exception needs the user's approval. `canopen/CANopenNode_STM32/` is a port already adapted to this project (`canopen/VERSIONS.md`); change it only with the user's approval.

## Hardware & toolchain
- Target: STM32G473VET6 (LQFP100, Cortex-M4F, `-mfpu=fpv4-sp-d16 -mfloat-abi=hard`) on a custom board; gate driver DRV8350S (SPI2), current-sense amplifiers AD8418.
- Toolchain & build: arm-none-eabi-gcc 14.3.1, CMake ≥ 3.22 + Ninja; C11, C++20. Build and size commands: see AGENTS.md › Commands.
- Code generator: STM32CubeMX (`stm32g4-foc-motor-drive.ioc`, toolchain CMake, `KeepUserCode=true`). Generated: `Core/`, `Drivers/`, `Middlewares/`, `cmake/stm32cubemx/`, `startup_stm32g473xx.s`, `STM32G473xx_FLASH.ld`. Edit generated files only inside `USER CODE` blocks. The root `CMakeLists.txt` is generated once and is free to edit.
- Pins, clocks, peripherals: HSE 24 MHz → PLL → SYSCLK 170 MHz. TIM8 centre-aligned PWM, period 4250 (≈ 20 kHz): high side INH_A/B/C = PC6/PC7/PC8, low side INL_A/B/C = PC10/PC11/PC12. Hall HAL_A/B/C = PA6/PA7/PB0 (TIM3). Phase currents CURR_A/B/C = PD13/PD11/PE8; phase voltages SENS_A/B/C = PD14/PD12/PD10; DC bus SENS_VDC = PA8 (ADC3/4/5). Board NTC PCB_TEMP = PC3 (ADC1_IN9, read by Monitor; 10k NTC to +3.3 V, 10k to GND, B assumed 3950, trip 85 °C → `DRIVER_OVER_TEMP`). DRV8350S: software SPI (SPI2 not used): DRV_SCLK = PB13, DRV_SDO = PB14 (input, internal pull-up), DRV_SDI = PB15, DRV_CS = PB12, mode 1, 200 kHz; DRV_ENABLE = PD15, FAULT_N = PE0. FDCAN1 RX/TX = PD0/PD1. LEDs: CAN_LED = PD2, PROCCESS_LED = PE1. Also CORDIC, DMA, USB.
  The pin, clock and peripheral setup in the `.ioc` is fixed; no other reserved pins or limits recorded (changes need the user's approval, see AGENTS.md › Always ask first).
- RTOS & memory budget: FreeRTOS 10.3.1, static allocation only. Tasks in `Core/Src/app_freertos.c` (higher number = higher priority): init 6 (2 KB stack, runs once, deletes itself; created in `main.c` from the `.ioc`), Supervisor 5 (2 KB, 1 ms), CANopen 4 (2 KB, 1 ms), Monitor 3 (1 KB, 10 ms), USB 2 (2 KB, `tud_task()`), Scrutiny 1 (2 KB, 1 ms). NVIC: EXTI0 and DMA1 Ch2/3 = 0, ADC3 = 1, DMA1 Ch1 = 4, FDCAN = 5, USB_LP/HP = 6, TIM6/SysTick/PendSV = 15; FreeRTOS critical sections mask priority 2 and below in importance, so 0 and 1 always run. Flash 512 KB, RAM 128 KB (linker script). Last measured: Debug flash 163.8/512 KB, RAM 34.4/128 KB; Release flash 97.9/512 KB, RAM 34.4/128 KB (2026-11-03).
  No explicit memory budget: report flash/RAM use with every build and flag large jumps. Task stacks are statically allocated arrays in `app_freertos.c`. A stack overflow or a failed `configASSERT` calls `RtosFatalError()`: MOE off, DRV_ENABLE low, then `Error_Handler()`.
- Debug & flashing setup: ST-Link via VS Code (`.vscode/launch.json`, `stlinkgdbtarget`), loads `build/Release/stm32g4-foc-motor-drive_tagged.elf`. For information only; flashing needs the user's approval every time.

- 2026-11-03 · Constraint: the DRV8350S SDO pin (open-drain) has no pull-up resistor on the board and the hardware cannot be changed. With only the MCU pull-up the line rises slowly, so the SPI2 peripheral fails even at its slowest 664 kHz. Software SPI in `drvTransfer()` (app.cpp) with 2.5 µs per half clock: 100/100 OK at ≥ 1 µs, 100/100 fail at ≤ 0.5 µs; keep ≥ 1 µs · Learned from: board tests 2026-11-03.
- 2026-11-03 · Decision: DRV8350S over SPI (`motor_control/drv8350s`). `powerOn()` writes 0x02–0x05 after the 2 ms wake-up and reads them back; a mismatch stops the start with `DRIVER_FAULT`. The nFAULT ISR only turns MOE off; ENABLE stays high until `drvFaultPoll()` (first call in SupervisorRun, ≤ 1 ms later) reads 0x00/0x01 into `drv_status` and maps VDS_OCP → `DRIVER_OVER_CURRENT`, OTSD → `DRIVER_OVER_TEMP`; then `powerOff()` · Why: ENABLE low resets the chip and its fault bits, so the cause must be read first; the software SPI (~85 µs per frame) is too slow for the priority-0 ISR. Register values (`DRV_CONFIG`, user's OK 2026-11-03, for BSC070N10NS5SC: Qgd 6 nC, RDS(on) 7 mΩ max, 5 Ω gate resistors): IDRIVEP/N 100/200 mA (~60/30 ns edges, TI's 100–300 / 50–150 ns guideline), dead time 100 ns on top of the VGS handshake (400 ns would be ~27 % of the 0.75 V back-EMF at 300 rpm), OCP latch (retry with CBC could clear the bits before drvFaultPoll reads them), OCP_ACT all half-bridges, VDS_LVL 0.4 V (~67 A cold / ~40 A hot, hot RDS(on) assumed ~1.5×), OCP_DEG 2 µs, TDRIVE 4000 ns.
- 2026-11-03 · Decision: regen limit by control (user's choice B, not a 0x6084 cap). The FOC ISR reads Vdc from the ADC5 DMA buffer, filters it (`VDC_LPF_ALPHA` 0.15, ≈ 0.33 ms) into `meas.vdc` and trips `OVER_VOLTAGE` there while the PWM runs; Monitor copies it to `status.Vdc` and still checks OV/UV every 10 ms (also in IDLE). `meas.regen_scale` goes from 1 at `VDC_REGEN_START` 27 V to 0 at `VDC_REGEN_STOP` 29 V; braking iq (iq · speed < 0) is scaled by it every ISR (`limit_braking_iq`, also in CURRENT mode), and the speed PI limit on the braking side is set to 9 A · scale at 1 kHz so the integral cannot wind up. The soft stop stays: it decides how to stop, the limit only slows braking near the trip · Why: a lab supply cannot sink current; board 2026-11-03, 3000 → 500 rpm at 0x6084 = 100000 rpm/s: before 23.4 → 30.8 V and OV trip in 37 ms, after max 28.5 V, no fault (Hall and SL). - 2026-11-02 · Decision: RPDO timeout needs no firmware code either: CANopenNode watches 0x1400:05 and 0x1401:05 (ms).
